About this panel

Every colour is one server instance behind the load balancer. This panel is pushed to every client once a second, regardless of which server it is attached to. With auto-rebalance on, servers holding more than their share ask some clients to reconnect, and the load balancer (least-connections) sends them to the emptiest server. Try: crash a server (Experiments), or --scale server=6, and watch the bars even out. Untick it to see connections stay skewed.

What it shows: Clients.All and Clients.Group reach every device on every server. The tag on each message is the server that handled the sender's call. Join rooms to see targeted delivery: messages to a room only reach its members.

    Target

    1 · Latency probe

    Round-trip time from this device to its server (WebSocket + load balancer). Compare phone on Wi-Fi vs. laptop.

    2 · Server burst (fan-out + backplane throughput)

    The server you're on publishes N messages to every connected client through Redis. Pick everyone or rooms (devices without a room join one automatically). Each device counts what it receives (loss, ordering, msgs/s) and reports back below.

    3 · Flood (many senders → many receivers)

    Each device sends tiny messages at the chosen rate, to everyone and/or to random rooms (devices join two random rooms A–C for the test, so room traffic only reaches members). Total deliveries/s = devices × rate × connections. Each device times its own messages coming back through Redis (end-to-end latency).

    4 · Virtual users (connection scale)

    Opens extra WebSocket connections from this browser (every one is a real client, spread over the servers). Ten phones × 200 = 2,000 connections. Each virtual user also receives all broadcasts.

    5 · Durable log: no message lost (audit)

    Every device sends numbered messages through the replicated log (Redpanda). Each receiver checks, per sender, that the numbers arrive without gaps. Start it, then crash a server, drain one, fail over Redis, or docker compose stop redpanda-2: GAPS must stay 0. A send that could not be persisted is retried with the same id until it is.

    6 · Resilience

    Abrupt: kills the instance you're on with no warning (like a power cut). Its clients notice, reconnect to the survivors and re-join their rooms; messages sent in the gap are lost.
    Graceful: the instance leaves the load balancer, asks its clients to move in small waves, and only then exits (what a rolling upgrade does). Compare the "moved … in Ns" lines in the log.
    Redis failover: Sentinel promotes a replica to primary. The app keeps serving; the Redis line in the cluster panel shows the new primary. (Try docker compose stop redis-1 too.)
